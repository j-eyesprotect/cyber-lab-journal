# Authentification SSH par clé et durcissement

## Contexte et objectif

Les VMs serveurs du labo (Ubuntu-DC, Ubuntu-01) ne disposent pas de copier-coller : toute administration se fait en SSH depuis PowerShell, sur le PC hôte Windows. Objectif : remplacer l'authentification par mot de passe par une authentification par clé, plus sûre et plus pratique à utiliser au quotidien, puis durcir la configuration SSH en conséquence.

## Génération et déploiement de la clé

Une paire de clés ed25519 est générée côté PC hôte Windows. Comme le copier-coller n'est pas disponible vers les VMs, la clé publique est déployée sur Ubuntu-DC via un pipe SSH, sans jamais avoir besoin de copier-coller manuellement le contenu de la clé. L'authentification par clé est testée et confirmée fonctionnelle.

Une réflexion est menée sur la sauvegarde de la clé privée : les deux pistes envisagées sont une clé USB dédiée et une pièce jointe dans KeePass, outil de gestion de mots de passe déjà utilisé par ailleurs.

## Un bug de collage résolu : passphrase et ssh-agent

Lors du déploiement de la même authentification par clé sur la VM Windows 11 du labo, un problème d'authentification est rencontré : la clé semblait refusée malgré une passphrase a priori correcte. Investigation : la passphrase était en réalité correcte, confirmée en la collant directement dans un PowerShell classique plutôt que dans Windows Terminal. Le blocage venait en fait d'un bug de collage propre à Windows Terminal et à son composant ConPTY sur les invites de passphrase.

Le contournement adopté est d'utiliser ssh-agent côté Windows : le service est démarré, la clé est chargée une fois par session Windows via ssh-add, ce qui permet ensuite de se connecter en SSH sans avoir à ressaisir la passphrase à chaque fois.

## Durcissement : désactivation ciblée du mot de passe

Sur Ubuntu-DC, l'authentification par mot de passe SSH est désactivée, mais uniquement pour le compte admincyber, via un bloc Match User dans sshd_config. Les autres comptes fictifs de l'entreprise (jrat, nlefevre, etc.) conservent l'authentification par mot de passe, car ils restent nécessaires pour de futurs exercices pédagogiques nécessitant ce mode d'authentification plus classique.

## Ce que ça m'a appris

Un problème qui ressemble à une erreur de mot de passe n'en est pas toujours une : ici, la passphrase était correcte depuis le départ, et le vrai problème venait d'un bug de collage dans un terminal particulier. Tester la même action dans un autre outil (ici, PowerShell classique plutôt que Windows Terminal) permet d'isoler si le problème vient de la donnée elle-même ou de l'outil utilisé pour l'entrer. Durcir une configuration SSH de façon granulaire, compte par compte, via Match User, est plus réaliste qu'un durcissement global : dans un vrai environnement, tous les comptes n'ont pas nécessairement le même niveau d'exigence de sécurité au même moment.
